3. HOW THE SITE LOADS
---------------------
This is a plain static site. There is no build step and no server
runtime required.

index.html loads js/app.js as an ES module. Do not rename index.html
to app.js, and do not rename or move the js/ or css/ directories.

The site uses hash routing:

    #/login-webui
    #/dashboard
    #/password-change

4. STATIC FILE SERVING - IMPORTANT
----------------------------------
The current server appears to return index.html for unknown paths,
including /caller/js/app.js. That is wrong for this package.

Every file must be served as a real static file:

    .js   -> application/javascript
    .css  -> text/css
    .html -> text/html

If /caller/js/app.js returns HTML, the browser will fail to load the
console. Check the response headers and body after deployment.

Also confirm whether /caller is currently a static directory or a
Node/Next/Cloudflare application. If it is a Node, Next.js, or
Cloudflare app rather than a static directory, SSH + copying files
may not be enough. Ask for that app's build and deploy process
before changing it.

5. TARGET PATH AND NGINX
-----------------------
Target filesystem path for a static nginx setup:

    /var/www/happyphone.lol/caller

If the console lives at /caller/console/, the target is:

    /var/www/happyphone.lol/caller/console

nginx location block for /caller/:

    location = /caller { return 301 /caller/; }
    location /caller/ {
        root /var/www/happyphone.lol;
        index index.html;
        try_files $uri $uri/ /caller/index.html;
    }
    location = /caller/console/password-change {
        return 302 /caller/console/#/password-change;
    }

nginx location block for /caller/console/:

    location = /caller/console { return 301 /caller/console/; }
    location /caller/console/ {
        root /var/www/happyphone.lol;
        index index.html;
        try_files $uri $uri/ /caller/console/index.html;
    }
    location = /caller/console/password-change {
        return 302 /caller/console/#/password-change;
    }

For a deployment at /caller/, use:

    location = /caller/password-change {
        return 302 /caller/#/password-change;
    }

The inline bootstrap alias in index.html also rewrites
/caller/console/password-change and /caller/password-change (with
or without a trailing slash) when the server falls back to
index.html for those paths.

The try_files fallback is only a safety net for the hash-routed app.
Real files such as /caller/js/app.js must still be found on disk
and served with a JavaScript content type.

7. TELNYX CREDENTIALS AND CONFIG
--------------------------------
The package ships js/config.js with blank values:

    username:  ''
    extension: ''
    password:  ''
    passwordChangeEndpoint: '/caller/console/api/password'

Dave can either:

  A. Edit js/config.js on the server with a Telnyx SIP username,
     agent extension, and SIP password, or
  B. Leave it blank and let agents enter their own values on the
     sign-in screen.

A Telnyx API key will NOT work in the browser WebRTC SDK. These are
SIP credentials, not API credentials.

Anything placed in js/config.js is served to every visitor and is
public. Do not put secrets there that must stay private. For real
production, prefer a server-side JWT/token flow so SIP credentials
never reach the browser.

Do not commit credentials to Git.

8. ONE PHONE NUMBER, MANY AGENTS
--------------------------------
Model B: one Telnyx SIP Credential Connection and one phone number,
with a separate Telephony Credential for each agent or device.

Multiple telephony credentials can share one connection and one
phone number. What that means:

  - All agents on the connection share the outbound caller ID.
  - The caller ID belongs to the connection/number, not the credential.
  - A telephony credential is a SIP identity, not a phone number.
  - Inbound routing is connection-level, not per-agent.
  - Telnyx recommends one telephony credential per device.
  - Do not share one credential across tabs or devices; registration
    conflicts will break calls.

9. PASSWORD CHANGE PAGE AND BACKEND
-----------------------------------
The console includes a password page at:

    #/password-change

It shows the signed-in SIP username and extension and posts JSON:

    {
      "username": "sip-username",
      "extension": "2041",
      "currentPassword": "current-password",
      "newPassword": "new-password"
    }

to TELNYX_CONFIG.passwordChangeEndpoint. The default is:

    /caller/console/api/password

If the config value is blank, the app falls back to the app-relative
path api/password.

The page is included and ready, but actual password changes require
Dave's backend endpoint. If the endpoint returns 404, 405, 501, or
cannot be reached, the page says password change is not enabled and
does not claim success.

For a deployment at /caller/, set passwordChangeEndpoint to
/caller/api/password, or leave it blank so the app uses the
app-relative api/password path.

Endpoint responses expected by the page:

  200/201 { "ok": true }
      -> sign out, clear the in-memory session, return to sign-in.

  200/201 { "ok": true, "username": "...", "password": "..." }
      -> show the new SIP credentials once with a copy button,
         then require re-login.

  400/401/403
      -> show the server's error or message.

  404/405/501 or network failure
      -> "Password change is not enabled on this server yet.
          Ask Dave to connect the password-change endpoint."

IMPORTANT TELNYX LIMITATION
The Telnyx Telephony Credential PATCH endpoint only updates name,
tag, connection_id, and expires_at. It CANNOT change sip_password
or sip_username. The page does not pretend it can PATCH a Telnyx
password.

Backend options:

  A. App-level extension passwords + short-lived JWTs (recommended).
     The backend owns agent passwords, verifies the current password,
     writes the new one, and mints a short-lived Telnyx JWT for
     sign-in. Password changes work without touching Telnyx.

  B. Delete and recreate the Telnyx telephony credential.
     This issues a new SIP username and password, so it is
     disruptive and must be coordinated with the agent. It is the
     only way to change a Telnyx SIP password directly.

The client never stores the current or new password in
localStorage or sessionStorage.
